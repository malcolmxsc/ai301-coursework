# Rubric: is this a good first issue?

## Checks

| Check                               | Evidence                                                                                                                                                                             | Pass condition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Weight    |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| Repository is not archived          | Repo-facts block: the `archived:` field on the repo line                                                                                                                             | Pass if the repo-facts block reports `archived: no`. Fail if it reports `archived: yes`. An archived repository is read-only and cannot accept a pull request, so no other evidence of liveness can rescue it. Grade this check before the others; if it fails, the issue is rejected regardless of how active the repository once was.                                                                                                                                                                              | required  |
| Maintainer liveness                 | Repo-facts block: the maintainer first-response sample, then the last 5 default-branch commit dates                                                                                 | Apply these two steps in order. Step 1: pass if at least one issue in the maintainer first-response sample shows a maintainer first response, whatever the delay and however many other sampled issues went unanswered — one documented response proves maintainers are still answering. Step 2: if no sampled issue shows a response, or the sample is empty, fall back to commit activity and pass if the repo-facts block lists at least one default-branch commit within 30 days before the bundle's capture date. Do not require the bundle to identify commit authors as maintainers; a default-branch commit is landed by someone with write access, and the bundle names no maintainer roster. Fail only when both steps fail: no sampled issue shows a maintainer response and no default-branch commit falls within 30 days before the capture date.                | required  |
| Repository activity                 | Repo-facts block: last 5 default-branch commit dates                                                                                                                                 | Pass if at least one default-branch commit occurred within 30 days before the bundle's capture date.                                                                                                                                                                                                                                                                                                                                                                                                                    | preferred |
| Newcomer-friendly scope             | Issue body, linked issues, issue labels, and the whole comment thread, read for whether the thread reaches a decision                                                                | Pass if the change is already decided: the issue or its thread makes clear what behavior or result the maintainers want, so a contributor can start work without first settling that question. Brevity is not a failure — a terse but concrete bug report or maintainer-filed task passes even when it states no completion criteria, provided the intended change is unambiguous. Multiple files or implementation steps do not by themselves make an issue too broad, and optional extras, stretch ideas, or further suggestions listed alongside a clear primary change do not fail it; grade the primary change. Fail if the issue is an umbrella, tracking, or megaissue collecting multiple independent pieces of work; if it requires a repository-wide sweep; if the desired behavior is still contested, shown by a thread of competing proposals, unresolved design questions, or abandoned attempts with no settled conclusion; or if it is a bare feature wish whose intended behavior maintainers have not yet decided. | required  |
| No active contributor               | Issue assignee field, the linked-PR list in the repo-facts block (with each PR's open/closed/merged state), and claim comments in the issue thread                                   | Pass if nobody is currently assigned to the issue, no linked or referenced pull request is open, and no unexpired claim comment stands. Fail if an assignee is set, or if any linked or referenced pull request is open: an open PR is live work on the issue no matter how long it has sat idle, and the staleness exception below never applies to one. Closed or merged pull requests are not claims. The staleness exception applies to claim comments only: a comment claiming the issue that is more than 30 days old at the bundle's capture date, with no subsequent activity from that contributor and no open PR of theirs, counts as stale and does not fail this check. | required  |
| Contribution policy allows the work | `CONTRIBUTING.md` or other repository contribution-policy text identified in the evidence bundle or `references/evidence-guide.md`                                                   | Pass if there is no explicit repository policy prohibiting the contribution workflow. Fail if the repository explicitly prohibits AI-generated or AI-assisted contributions, or otherwise states a policy that would prohibit this contribution. The absence of such a restriction counts as pass.                                                                                                                                                                                                                      | required  |
| Contributor documentation           | `CONTRIBUTING.md` and README setup or contribution instructions                                                                                                                      | Pass if the repository has either a `CONTRIBUTING.md` file or clear setup and contribution instructions in the README.                                                                                                                                                                                                                                                                                                                                                                                                  | preferred |
| Good first issue signal             | Issue labels                                                                                                                                                                         | Pass if the issue has a `good first issue`, `help wanted`, beginner, newcomer, or equivalent label.                                                                                                                                                                                                                                                                                                                                                                                                                     | preferred |

## Verdict rule

Accept the issue if every required check passes.

Reject the issue if any required check fails or is unclear.

Preferred checks never change the accept or reject verdict. They are used only to rank issues that already pass all required checks.
